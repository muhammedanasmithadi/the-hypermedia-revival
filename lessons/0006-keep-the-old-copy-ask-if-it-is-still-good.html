Hypermedia: the handshake that keeps your copy fresh

A stored reply saves a wire round trip until its copy turns stale. Then you ask: is it still good? This section runs the ask, and the 304 that answers.

Section 06

Keep the old copy. Ask if it is still good.

Section 05 sorted the methods by harm and repeatability. This section shows how the browser keeps a copy and asks the server whether the copy is still good.

Before you read on: in Sections 01 and 03, why did the kiosk and the explorer re-draw their whole screens on every move?

Each move changed the URI or the document, so any stored copy would have gone stale. Those clients did not know how to ask whether their copies still matched the server.

Store the response

Fielding adds the cache constraint to the stateless style. A response is labeled cacheable or not. A cache may reuse that response data for later, equivalent requests.

Your browser runs a cache for you. It stores reply bodies after a safe request. The URI labels which replies match, so a later request to the same URI may fetch the stored copy rather than the network.

Caching works because each URI is its own state. The server keeps no session per connection. A later request to the same URI sends a copy the cache kept, instead of a new reply.

Read the method

The method picks the default. Fielding writes that the response to a retrieval request is cacheable. The response to other requests is not cacheable, but control data may override the label.

RFC 9110 refines that rule. A GET or HEAD answer is cacheable by default. A POST answer joins the cache only when the reply names the stored copy in a Content-Location header and proves its own freshness with a date or seconds. A PUT, DELETE, or OPTIONS answer stays out of the cache.

Try it now

Open the developer tools and the Network tab. Reload this page. Click any request. Read its response headers. On many sites you will find Cache-Control, ETag, or a date that says how long a copy may stay fresh. Read this page's response headers. This deployment sends Cache-Control: max-age=600, an ETag, and a Last-Modified date. The cache control sets the lifetime: ten minutes. ETag and Last-Modified are validators, not lifetimes. Check the freshness

RFC 9111, the HTTP caching specification, says freshness decides reuse first. A cache reuses a fresh copy without asking the server. Only a stale copy triggers a new request.

Expires sets a date. Cache-Control max-age sets a number of seconds and wins when both appear. Together they guard the lifetime of the stored copy.

Age counts seconds since the server or an earlier cache made or refreshed the copy. As long as the age stays below the lifetime, the copy stays fresh.

Ask the fingerprint

A stale copy does not die. The cache keeps it and asks the server: is this copy still good? RFC 9110 calls the answer mechanism a validator. The two most common validators are an entity tag (ETag), a fingerprint the server sets, and a date from Last-Modified.

The cache sends the fingerprint back in a conditional header. If-None-Match carries the ETag. If-Modified-Since carries the date. The server compares the two, and a match earns a small reply.

Get 304, keep the copy

A matching fingerprint earns a 304, Not Modified. The reply carries no body. The client keeps its stored copy and refreshes its age. The next fetch starts the clock again.

A 200 replaces the copy. A 304 keeps it. The difference saves time over slow links and keeps cached pages fast on the mobile web.

The handshake, in review

Review what the fetch and the conditional ask showed you.

  1. A cache stores reply bodies and reuses them for later, equivalent requests.
  2. Freshness decides reuse first. Expires or max-age set the lifetime; Age counts elapsed seconds.
  3. A fresh copy never asks the server. A stale copy does.
  4. An ETag fingerprints a version; If-None-Match sends it back.
  5. A match earns 304, no body; the client keeps its copy and refreshes its age.

Check yourself

Three questions follow. Answer each one before you open it.

Your browser stored a page at 12:00 with Cache-Control max-age 600. You request it again at 12:05. Does the browser ask the server?

No. 600 seconds is ten minutes, so the copy stays fresh until 12:10, and five minutes is below the lifetime.

The copy turns stale at 12:20. What does the browser send to ask if it is still good?

It sends If-None-Match carrying the ETag it stored, or If-Modified-Since carrying a date, so the server can compare.

The server has the same ETag. It answers 304, Not Modified, with no body. What does the browser do with its copy?

It keeps the copy as valid and refreshes its age so the next freshness window starts again.
