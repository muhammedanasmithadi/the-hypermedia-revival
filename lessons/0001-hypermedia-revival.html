Section 01

The machine that prints its own manual

Here is a machine you have never used: a card payment terminal at a supermarket checkout. You have no manual and no training. You have no intention of reading one.

You start anyway. You insert the card and tap the screen. The terminal shows only the moves it allows at that moment. Choose a move, and the next screen shows the moves that remain. It never offers a move you cannot take, and it never shows the full manual at once.

You already know this pattern. You have described links and forms for years. Keep that thought, and use the terminal below. It behaves like the whole web.

The terminal holds the rules. You do not. It shows cash-out options only after it knows your balance. Deposit ten dollars, and the menu changes; an option it refused before now appears. The terminal prints its own manual one screen at a time, and it prints each page only when you can act on it.

The web is the same machine, run at a distance. A website is a server with a screen you hold. When it answers, the reply carries both the facts and the actions in one body: the balance and the buttons.

Before the experiment, make a guess. The server knows your balance: forty dollars. One reply carries the fact alone. One carries the fact and the buttons. Which one can you use without instructions? Choose a reply type, then compare the two.

GET /account/balance

Both replies carry the same fact: forty dollars. You can switch between them at any time. Only one arrives with its own controls. That reply is a document. The word for documents like this one is hypermedia.

Define the term once, while both replies stay on screen. A hypermedia system sends information and controls together, in one document, so the document teaches you what to do through the buttons it carries. The controls are links, buttons, and forms. The industry calls controls that drive the application forward HATEOAS: hypermedia as the engine of application state.

Now consider the other reply. A raw JSON number carries one fact and no controls. To use it, the client must already know the moves, from a spec or from a conversation no one wrote down. The manual has moved off the document and into the code that receives it, where it stays until someone updates it.

Browse a GitHub repository and you hold documents with buttons. Ask its API and you get JSON.

If your balance changes at midnight, which client survives? The one that reads documents survives, because it does what the next page offers. The JSON client must be told again, rebuilt, and shipped. You have seen both cases now: the terminal changed its menu, and the server changed its reply.

The machine that prints its own manual has a name and an architect. Roy Fielding described it in his doctoral dissertation in 2000, and again in 2008. By then the industry had borrowed his word REST and attached it to a different machine.

Count the plain controls on this page: the section anchor, the GET line above, the source link. The browser resolves each one by itself. The page runs no custom code for these controls. That is the whole job.

Now consider the wider view. Everything a hypermedia application does is one loop, repeating. Read the loop as a sentence, then step through it.

user picks a control
→
Document

→

→

server advances state
The user clicks a link or a button. The browser turns that control into a request to the server.

Request. Document. Choice. Next document. The machine advances its state only when it answers you, and nothing else drives a hypermedia application.

Three ideas carry through the rest of this document.

01 The document is the point of contact. The interface is delivered, not rebuilt.
02 The server is the logical center. State becomes options; the client renders.
03 The manual rides along. The client fetches and follows; it never guesses.

This is a choice, not a law. Most software today answers with JSON and rebuilds its own interface in the browser. It works, at the price of a client that must be rewritten and shipped whenever the rules change. The same trade-off buys offline apps and richer interactivity.

So here is the question at the center of this document: the web shipped with documents and controls built in. Why did our industry spend a decade sending data instead of controls?
