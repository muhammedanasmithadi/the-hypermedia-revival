Two architectures on the same table

Section 01 ran one loop: request, document, choice, next document. Section 02 traced where that loop went. Now lay one feature on the table twice, once as documents and once as JSON, JavaScript Object Notation, values under a contract, and compare the two with the same clicks.

Before you read on, can you name the loop in four words, and say who held the next move by the end of Section 02?

The client. The JSON decade moved the manual off the document and into the code that receives the payload.

Take one account

One account at one bank: account 4027, with a balance of forty dollars. The bank serves the same feature from two buildings. Building A answers every request with text/html. Building B answers every request with application/json.

Both buildings start with the same three moves: check the balance, pay the bill, view the receipt. The same clicks bring the same facts, and each side of the table runs its own loop.

Building B has strengths this section does not test: a screen that stays live, richer gestures, offline work. The comparison stays on one question: who names the next move?

Try it now

Pick a page you use often. Open DevTools with Ctrl+Shift+I (or Cmd+Option+I), reload, and click the page’s own buttons. Find the JSON replies in the Network tab. Now label the building: did any reply name the buttons it rendered, or did the page compile them beforehand?

The comparison, in review

Review what the two lanes just showed you.

  1. Every click got two replies, in two shapes: a document with controls, and values with a contract.
  2. The document named the next moves. The payload named none.
  3. Building A’s app can meet any new move the server types. Building B draws its menu from the build it shipped.
  4. Rules change instantly in one building, and after a release in the other.

Read both replies

Read the same click in both shapes. Below, the move “apply the credit” arrives once as Building A answers and once as Building B answers. The first reply carries the next move inside itself. The second carries a value. The contract lives outside the reply, in the spec.

Fielding named the difference between the two in 2008. The quote below is his own list of what each architecture leans on.

The two names are the two buildings. Data-oriented integration sends the values under a contract, and the client carries the rulebook. Control-oriented integration sends the moves with the values. You do not need to memorize the two names yet. Controls ride with the facts, or they live in a separate contract.

Track the new move

You let a night pass in the demo, and the bank legalizes a $10 credit overnight. Building A served the new move with the next reply: a new button, with no update to the client at all. Section 01 asked which client survives a midnight change. This is that change, on the table.

Building B served the new value with the next reply, and kept its menu. Because the app draws that menu from the build it shipped, the new move waits for a new release. Section 02 named this exact cost: the client must be rebuilt and shipped again.

Fielding also said when to care: long-lived systems that cross teams earn the extra constraint, and a short-lived wrapper usually does not. From the same comment: “If you don’t see a need for the constraints, then don’t use them. That’s fine with me as long as you don’t call the result a REST API.”

Building B keeps its strengths: richer screens, live state, offline work. The comparison never claimed otherwise. It asked one question, and it answered it: the moves live with the facts, or they live in the shipped client. You do not need the HTTP, Hypertext Transfer Protocol, status codes yet. The wiring details don't change the answer.

Say who holds it

Before the self-check, say the answer in your own words. Who names the next move in each building?

Building A names it in the reply, where the server decides. Building B names it in the client’s build, where the contract decided. That is the difference Fielding put in words: data-oriented integration against control-oriented integration.

Check yourself

Three questions follow. Answer each one before you open it.

Two buildings, one account. Which building names the next move in its reply?

Building A. Its document carries the links and forms. Building B’s payload carries values, and the app draws the moves from its build.

The bank makes a new move legal overnight. Which building shows it before a new app build ships?

Building A. The server types the new move into the next reply. Building B waits for the app to be rebuilt and shipped.

Say Fielding’s distinction in your own words.

Data-oriented integration sends the values under a contract, and the client holds the moves. Control-oriented integration sends the moves with the values, in the document.

The table has two sides, and the cost shows when rules change: one building types the new move, the other ships it. You can now answer “who names the next move?” for any feature, and the answer tells you where the manual lives.
