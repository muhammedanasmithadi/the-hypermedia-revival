Hypermedia: the architecture the web was built on

A short, interactive explanation of the web’s original architecture. We still build on it, mostly without naming it. The interactive demos below explain the ideas.

Section 01

The machine that prints its own manual

Run the machine

Sooner or later you meet a machine you have never used: a card payment terminal at a supermarket checkout. There is no manual, no training, and you have no intention of using either. You read the screen instead. This section gives the pattern a name, a loop, and an architect.

You insert the card and tap the screen. The terminal shows the moves it can keep at that moment and refuses a choice it cannot honour. Choose a move, and the next screen shows the moves that remain. It never shows the full manual at once.

You already know this pattern. You've spent years on websites that behave exactly this way, and you may never have given them a name. Use the terminal below before we give one.

terminal · training unit welcome
Card payment terminal
This little machine shows you the moves of the moment, and refuses a choice it cannot keep.
balance: $40

The terminal holds the rules. You do not. It shows cash-out options only after it knows your balance. Deposit ten dollars, and the menu changes; an option it refused before now appears. The terminal prints its own manual one screen at a time. It prints each page only when you can act on it.

Keep this as the first rule of the course: operate the machine before you define it. You have run the machine. Wait until the definition. It reads faster after the run.

The web is the same machine, run at a distance. A website is a server with a screen you hold. When it answers, the reply carries both the facts and the actions in one body: the balance and the buttons.

You might wonder why the machine keeps its options hidden. It hides them because the state decides what you may do. A balance of forty dollars has no fifty dollar rule. The same logic now travels across a network.

Choose a reply

Before the experiment, make a guess. The server knows your balance: forty dollars. One reply carries the fact alone. One carries the fact and the buttons. Which one can you use without instructions? Choose a reply type, then compare the two.

GET /account/balance

Both replies carry the same fact: forty dollars. You can switch between them at any time. Only one arrives with its own controls. That reply is a document. The word for documents like this one is hypermedia.

The number beside the request line ended the same way each time: 200 OK. Two hundred means the document reached you whole. That switch was one turn of the loop the course names below. You do not need the other numbers yet; Section 04 names them.

Try it now

Press Ctrl+U (or Cmd+Option+U in Chrome and Safari; Cmd+U in Firefox) to view this page’s source. The HTML, HyperText Markup Language, tab that opens is this whole document in plain text. The links and buttons the author typed in appear there as small tags. The demos create the rest of their controls while they run. Do not read it. The document describes itself. That list is the loop, running on this page. Close DevTools once you have seen it.

Name the pattern

Define the term once, while both replies stay on screen. A hypermedia system sends information and controls together, in one document. The document teaches you what to do through the buttons it carries. The controls are links, buttons, and forms. The industry calls controls that drive the application forward HATEOAS: hypermedia as the engine of application state.

Say that definition back to yourself in two sentences, before you read on.

You don't need to memorize the acronym yet. You used the idea the moment you read the terminal and the experiment. The name will keep appearing through the course. What matters is the shape: the controls ride with the facts.

Now consider the other reply, the raw JSON, JavaScript Object Notation, reply that carries one fact and no controls. To use it, the client must already know the moves. The moves come from a spec or from a conversation no one wrote down. The manual has moved off the document and into the receiving code. It stays there until someone changes the code.

Browse a GitHub repository and you hold documents with buttons. Ask its API, Application Programming Interface, and you get JSON.

If your balance changes at midnight, which client survives? The one that reads documents survives, because it does what the next page offers. The JSON client must be told again, rebuilt, and shipped. You have seen both cases now: the terminal changed its menu, and the server changed its reply.

The machine that prints its own manual has a name and an architect. Roy Fielding described it in his doctoral dissertation in 2000, and again in 2008. By then the industry had borrowed his word REST, Representational State Transfer, and attached it to a different machine.

Watch the loop

Now consider the wider view: everything a hypermedia application does is one loop, repeating. Read the loop as a sentence, then step through it.

Request
user picks a control
Document
facts + controls
Choice
user selects a move
Next document
server advances state
The user clicks a link or a button. The browser turns that control into a request to the server.

Request. Document. Choice. Next document. The machine advances its state only when it answers you, and nothing else drives a hypermedia application.

The section, in review

Review the section in four points.

  1. One document delivers facts and controls in a single body.
  2. A picked control becomes a request; the browser asks the server.
  3. The server reads state and answers with a fresh document.
  4. The loop repeats, and nothing else drives a hypermedia application.

Three ideas carry through the rest of this document.

01 The document is the point of contact. The server delivers the interface; the client never rebuilds it.
02 The server is the logical center. State becomes options; the client renders.
03 The manual rides along. The client fetches and follows; it never guesses.

Check yourself

Three questions follow. Answer each one before you open it.

A stranger’s page offers buttons you have never used. What lets you act without calling anyone for help?

The document arrives with its own controls, so the page teaches you the next move. You read the buttons, and you act.

You deposit money, and the menu grows a new button. Who decided that button exists: the device in your hand, or the machine on the network?

The machine on the network. Its state sets the rules, and the document it sends carries the new button. Your device only renders it.

Say the loop that drives a hypermedia application, in your own words.

Request, document, choice, next document. Every click sends a request and gets a fresh document back.

This is a choice, not a law. Most software today answers with JSON and rebuilds its own interface in the browser. It works, at the price of a client that developers must rewrite and ship whenever the rules change. The same trade-off buys offline apps and richer interactivity.

So here is the question at the center of this document: the web shipped with documents and controls built in. Why did our industry spend a decade sending data instead of controls?
