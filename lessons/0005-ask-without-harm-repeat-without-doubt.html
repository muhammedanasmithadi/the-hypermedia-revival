Hypermedia: the two tests that guard your repeats

A safe method changes no state. An idempotent method repeats with the same effect. This section sorts six methods by both tests, then replays a dropped connection.

Section 05

Ask without harm. Repeat without doubt.

Section 04 read what happened after a move. The harder question comes before you send it: which requests may you send twice? This section names two tests that keep a retry safe.

Before you read on: in Section 03’s fetch-built app, who decided that the GET path is harmless?

The app’s own code decided it. The JSON payload carried no controls, so the safety promise lived outside the document. This section names that gap.

Sort the methods by harm

A safe method changes no server state. Check an account, read a balance, ask what a resource allows. State stays as it was.

GET, HEAD, and OPTIONS are safe. GET, Hypertext Transfer Protocol’s read verb, carries the document. HEAD asks for the headers only, without the body. OPTIONS asks what the server allows on a resource. None of them writes. TRACE is safe too, but servers rarely serve it. This course passes it by.

Safety protects the link, and a browser may follow a GET before you click it. A preloader, a crawler, or a preview box all reuse one request, and none of them asks first.

The fetch-app in Section 03 drew its own moves. Your browser trusts a GET to be harmless. Break that trust, and a blind preloader changes state without a click.

Sort the methods again, by repeatability

Repeatability is the second test. Send the same move twice: does the same state come out? An idempotent method changes nothing more on the second send than on the first.

PUT and DELETE are idempotent. POST, Hypertext Transfer Protocol’s create-or-pay verb, is not. Send a payment twice, and you may be charged twice.

The two tests separate. DELETE removes state, yet two DELETEs leave the same result. One method can be unsafe and idempotent at once. Only the repeat test says whether a blind retry can double the move.

A reply can vanish, and the lost reply never proves the server ignored the request. A mobile network, a closed lid, a crash: the server may have moved already. Repeatability protects the retry.

      Keep harm off harmless asks

      RFC 9110, the HTTP, Hypertext Transfer Protocol, specification, puts the action on the resource owner. An unsafe action must never ride on a safe method. Some pages bury a delete in a query string that a GET loads. A preloader may fire that GET blind.

      Keep harm off GET, and keep doubt off POST. Then a link stays a link, and a retry stays a retry. You do not need the cache handshake yet. Section 06 carries it.

      Before the check, say the answer in your own words. Which test does POST fail?

      The repeat test. Two POSTs can move the state twice.

      The two tests, in review

      Review what the sort and the replay showed you.

      1. Safe methods change no state. GET, HEAD, and OPTIONS pass that test.
      2. Idempotent methods repeat with the same effect. PUT and DELETE pass that test.
      3. POST fails the repeat test. Send it twice, and the move may land twice.
      4. The two tests separate. One method can be unsafe and idempotent at once.

      Check yourself

      Three questions follow. Answer each one before you open it.

      Which three methods pass the harm test?

      GET, HEAD, and OPTIONS. None of them changes server state.

      You send a payment by POST. The connection drops. A retry sends the same POST again. What happens if the first one landed?

      A second charge. POST is not idempotent, so a blind retry doubles the move.

      You delete a row by DELETE. The first try returns 200, and the retry returns 404. Does 404 break idempotence?

      No. The row left on the first try. The second reply only says the row is gone.

      Two tests, one connection. The method column names what a move may do, and the status line names what it did. Section 06, “Keep the old copy. Ask if it is still good,” shows the stored-copy handshake that still makes a page fast on a slow connection.

      The companion book hypermedia.systems, by Carson Gross, Adam Stepinski, and Deniz Akşimşek, names the safe and idempotent corners of each method plainly.
